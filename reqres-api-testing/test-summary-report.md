Несмотря на то, что все тест-кейсы имеют статус Passed, в ходе тестирования выявлено 4 дефекта. Это объясняется тем, что тест-кейсы заранее предусматривали несколько возможных исходов, и оба варианта (соответствие или несоответствие ожидаемому REST-поведению) считались допустимым результатом теста.

## Ключевые находки

Отсутствие серверной валидации на POST /products. Несмотря на пометку 'required' в документации, сервер не проверяет: отсутствие полей, корректность названий полей, дублирование ключей внутри JSON, уникальность данных между продуктами. Единственная проверка, которую сервер выполняет — синтаксическая валидность самого JSON.

Сервер игнорирует значение id, переданное клиентом в теле POST-запроса, и всегда присваивает собственное значение (в рамках тестовой сессии — стабильно id: 21, что также указывает на отсутствие реального инкремента между запросами).

Аналогичное отсутствие проверок обнаружено и на GET /products/{id}: при запросе несуществующего id сервер возвращает код 200 Success с пустым телом вместо более ожидаемого кода 404 Not Found.

GET /products/{id} не выполняет проверку корректности id. Во всех случаях сервер возвращает 200 Success с пустым телом вместо ожидаемых 404/400.

В отличие от GET, PUT корректно проверяет тип id, но не проверяет существование ресурса при валидном числовом id.

DELETE /products/{id} демонстрирует такой же паттерн, как PUT: тип id проверяется корректно, но существование ресурса не проверяется.

## Общая оценка качества API

API FakeStoreAPI (v2.1.11) корректно выполняет запросы с валидными данными — базовые CRUD-операции над ресурсом Products работают предсказуемо и в соответствии с документацией. Однако в случаях с некорректными данными API работает ненадёжно: отсутствует валидация обязательности и корректности полей, а также проверка существования ресурса при обращении по id. Такое поведение объясняется слабо настроенными фильтрами проверки входных данных. Учитывая, что FakeStoreAPI — учебный/демонстрационный сервис, эти находки не критичны для его основного назначения, но в production-системе аналогичное поведение представляло бы серьёзный риск для целостности данных и безопасности.
