# Test Plan: Fake Store API Testing

## 1. Введение

Этот документ описывает план тестирования публичного API [https://fakestoreapi.com/](https://fakestoreapi.com/). Цель работы – применить навыки ручного тестирования на практике.

## 2. Цели и задачи

### Цели:
- Убедиться, что все основные CRUD-операции над ресурсами API корректно работают и API адекватно обрабатывает некорректные запросы.

### Задачи:
- Изучить документацию fakestoreapi.com, чтобы корректно составить тест-листы и тест-кейсы.
- Протестировать все запланированные эндпоинты, задокументировать найденные дефекты в виде баг-репортов.
- Сделать выводы из проделанной работы.

## 3. Описание тестируемого продукта

Fakestoreapi.com – это бесплатный RESTful API для прототипирования, тестирования или обучения. FakeStoreAPI предоставляет реалистичные данные электронной коммерции: продукты, тележки, пользователи и многое другое, доступные за секунды через REST.

FakeStoreAPI предоставляет 4 основных ресурса:

| Ресурс | Описание | Количество |
|---|---|---|
| Products | Список товаров с заголовком, ценой, категорией, описанием и изображением | 20 продуктов |
| Carts | Имитирует логику корзины покупок: пользователь + список идентификаторов товара + количество | 20 корзин |
| Users | Включает полные профили пользователей (имя, адрес электронной почты, адрес и т.д.) | 10 пользователей |
| Login | Возвращает токен JWT для тестирования аутентификации | JWT токен |

## 4. Область тестирования

**В область тестирования входит:**
- `GET /products` (получение списка всех продуктов)
- `GET /products/{id}` (получение одного продукта)
- `POST /products` (создание продукта)
- `PUT /products/{id}` (обновление продукта)
- `DELETE /products/{id}` (удаление продукта)

**Вне области тестирования:**
- Ресурс Carts
- Ресурс Users
- Ресурс Auth (авторизация/JWT)

## 5. Ресурсы и расписание

### Ресурсы:
- Инструмент тестирования: Postman
- Исполнитель: автор проекта (тестирование выполняется единолично)

### Расписание:
- Изучение документации и составление плана: 2 часа
- Проектирование тест-листов и тест-кейсов: 3 часа
- Выполнение тест-кейсов: 2 часа
- Оформление баг-репортов и подведение итогов: 2 часа

## 6. Стратегия тестирования

### Виды тестирования:
- Функциональное тестирование
- Негативное тестирование

### Применяемые техники тест-дизайна:
- **Equivalence Partitioning** — для проверки полей `price`, `title`, `category`
- **Boundary Value Analysis** — для проверки граничных значений `price` и `id`
- **Error Guessing** — для проверки нестандартных сценариев

### Метод тестирования:
Black Box

## 7. Критерии приемки

- Выполнены все тест-кейсы и заполнены все тест-листы.
- Задокументированы все дефекты в виде баг-репортов.
- Проведён анализ результатов и сделаны выводы проделанной работы.

## 8. Ожидаемые результаты

Тест-кейсы, чек-листы, баг-репорты, экспортированная Postman-коллекция.

## 9. Риски и предположения

Недоступность публичного API, изменение структуры ответов без предупреждения, неактуальная документация.

## 10. Организация и коммуникация

Все роли (тест-дизайн, выполнение тестирования, оформление документации) выполняются автором проекта самостоятельно.
