# Observations: Fake Store API — Products

**Отсутствие серверной валидации на POST /products**
Несмотря на пометку 'required' в документации, сервер не проверяет: отсутствие полей (TC-PROD-004, TC-PROD-005), корректность названий полей (TC-PROD-006), дублирование ключей внутри JSON (TC-PROD-008), уникальность данных между продуктами (TC-PROD-009). Единственная проверка, которую сервер выполняет - синтаксическая валидность самого JSON (TC-PROD-007, где невалидный JSON корректно вернул 400 Bad Request).

Сервер игнорирует значение id, переданное клиентом в теле POST-запроса, и всегда присваивает собственное значение (в рамках тестовой сессии - стабильно id: 21, что также указывает на отсутствие реального инкремента между запросами).

Аналогичное отсутствие проверок обнаружено и на GET /products/{id}: при запросе несуществующего id (TC-PROD-012) сервер возвращает код 200 Success с пустым телом вместо более ожидаемого кода 404 Not Found.

GET /products/{id} не выполняет проверку корректности id: несуществующий id (TC-PROD-012), id=0 (TC-PROD-013), id больше максимального (TC-PROD-014), отрицательный id (TC-PROD-015), нечисловой/дробный id (TC-PROD-016, TC-PROD-017) - во всех случаях сервер возвращает 200 Success с пустым телом вместо ожидаемых 404/400.

В отличие от GET, PUT корректно проверяет тип id (нечисловой/дробный id возвращает 400 Bad Request - см. TC-PROD-021, TC-PROD-022), но не проверяет существование ресурса при валидном числовом id (см. BUG-003).

DELETE /products/{id} демонстрирует такой же паттерн, как PUT: тип id проверяется корректно (нечисловой/дробный id возвращает 400 Bad Request - см. TC-PROD-026, TC-PROD-027), но существование ресурса не проверяется (несуществующий, но валидный числовой id, включая id=0, возвращает 200 Success - см. TC-PROD-024, TC-PROD-025).
